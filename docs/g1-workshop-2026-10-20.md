# G1 upgrade from 0.4.1 through the Workshop route, 2026-10-20

Related: [upgrade-041-2026-10-11](upgrade-041-2026-10-11.md) · [RELEASE-0.5.0](RELEASE-0.5.0.md) · [testing](testing.md)

Gate (RELEASE G1): a real 0.4.1 install with priorities and limits is upgraded
through the Workshop route and a file diff shows every saved row intact. The
manual route passed on 2026-10-11.

## How the game's mod loader handles a Workshop mod

- Subscribed Workshop items sit in `steamapps/workshop/content/1623730/<id>`
  (Pal Work Priority: 3786408856, holding the published 0.4.1). Active ones are
  listed in `Mods/PalModSettings.ini` (`ActiveModList=PalWorkPriority`).
- On launch the loader copies an active item into the game by its Info.json
  install rules: `Scripts` to `Mods/NativeMods/UE4SS/Mods/PalWorkPriority/`,
  the pak to `Pal/Content/Paks/LogicMods/`, and records every file it wrote
  in `Mods/ManagedMods/PalWorkPriority/InstallManifest.json` (0.4.1: 23
  Scripts files including `Scripts/config.lua`, the pak, Info.json).
- An update is detected by the item's Info.json version: after the item's
  files changed from 0.4.1 to 0.5.0-rc1 the loader reinstalled on the next
  launch (LastInstallTimeUtc 17:11:45 UTC). It deletes the files of its
  previous manifest and writes the new ones; it keeps no backup (`"Backups":
  []`). Files it did not install (priorities.txt, caps.txt, priority.log, the
  new root config.lua) are left alone.

## The test

Script `tools/g1_workshop_route.py` (prepare, seed, update, check, restore);
state and backups in `D:\PalWorkPriority-backups\g1-workshop-20261020-190819`.

1. Prepare: backups of PalModSettings.ini, mods.txt, the Workshop item and
   ManagedMods; the dev install and its pak moved aside; the Workshop item
   activated.
2. Launch: the loader installed the Workshop 0.4.1 (UE4SS log "Pal Work
   Priority 0.4.1 loaded", 19:08:38).
3. Seed (game closed): the priorities.txt and caps.txt that 0.4.1's own code
   wrote on 2026-10-11 (39 priority rows, 2 limit rows; the X rows had already
   been dropped by 0.4.1's bug) and a user edit in the installed
   `Scripts/config.lua` (`interval_seconds = 11`).
4. Update: the Workshop item's files replaced by the 0.5.0-rc1 Workshop
   archive built by `tools/release.py` from 172eccf (65 files, no DLL), as a
   Steam download would; `.workshop.json` kept. This step stands in for Steam's
   own download; the loader part is real.
5. Launch: the loader installed 0.5.0-rc1; "0.5.0-rc1 loaded", PWP_READY
   settings=available, the stand drew the 0.4.1 values, no WARN or ERROR.
6. Check (game closed): files copied to `test-results/g1-workshop-20261020/`.

| Check | Result |
|---|---|
| priorities.txt rows | identical (39) |
| caps.txt rows | identical (2) |
| `Scripts/config.lua` (with the user's edit) | deleted by the loader before 0.5.0 ran |
| root `config.lua` | created from the shipped defaults (`interval_seconds = 10`): **the 0.4.1 edit is lost** |
| `config.migration.bak` | holds the shipped defaults, not the user's file |

7. Restore: everything moved back; dev install, pak and Workshop item
   identical to before (hash check), PalModSettings.ini and mods.txt from the
   backup, the user's data files unchanged.

## Verdict

**Every saved priority and limit row survives the Workshop update: PASS.**
Edits a Workshop user made in 0.4.1's `Scripts/config.lua` are lost, because
the loader removes that file before 0.5.0 can migrate it; the mod cannot
prevent this (it runs after the loader). Settings changed through the in-game
options menu (DarnMenu) live in `Mods/shared/PalWorkPriority_user.lua`,
outside the loader's manifest, and are kept. The changelog tells Workshop
users to note their config.lua edits before updating. The final upload by the
user will be the real Steam download; this run covers the loader's part.
