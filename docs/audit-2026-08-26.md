# Audit, 26 August 2026

Nine independent read-only audits run against `b43578a`: bugs, UI, promises,
multiplayer, performance, Workshop comments, security, silent failures, release
readiness. Roughly thirty distinct findings, every one carrying a `file:line`.

This file exists because the previous audits were conversational and are gone.
Findings that are not written down are rediscovered, and this project has
rediscovered the same three or four faults more than once.

## Fixed so far

**Every finding in P0, P1, P2 and P3 is implemented.** Commits `a30e055`,
`fcb3fc3`, `046a5d5`, `e389168`, `d9eb995`.

| P0 | A1-A6 | nil guild refused; chat fails closed; off restores; Hello budgeted; the pass probes authority itself; current work protected |
| P1 | B1-B6 | integer-safe parsers; atomic writes; sandboxed `loadfile`; the icon pump stops asking the engine; the remote channel is opt-in; the stuck client flag cleared |
| P2 | C1-C7 | draws before showing; the top edge is pinned; Remove keeps its warning colour and disarms on screen; the toggle shows its state; names are consistent |
| P3 | all | click freshness gate; validation drops what it warns about; no blind send fallback on a client; three strikes before eviction; a client asks about a pal it has no data for; the wire width is named and checked |

**Found while fixing, not by any audit:** the `work_caps` loop variable is also
named `caps` and shadows the module, so reading `caps.MAX_CEILING` inside it
would have thrown during config validation and left the mod with no config.
`luacheck` cannot see that class of error.

### Found by testing the fixes, not by any audit

Three faults that only existed because of the audit work, all confirmed on a
live client and fixed:

- **The client never repainted a menu it had not drawn.** `M.refresh` consumed
  the repaint generation before `live_menu()` ran, so opening the stand after
  the data had arrived drew nothing at all - the numbers appeared only when a
  row happened to rebind, which is what clicking a vanilla checkbox does. The
  audit named this under B6 and only the click half was fixed.
- **The repaint gate was keyed on a name that is not unique.** Closing and
  reopening the stand builds a NEW instance whose cells carry the SAME
  generated full names, which `live_menu`'s own comment states. So the gate
  reported "same menu" for a tree whose sixty-two injected cells had just been
  dropped. It is keyed on a counter bumped by `forget_injected` now. This one
  was found by instrumenting after reasoning had produced two wrong answers.
- **An unresolved guild was delivered as an empty answer.** A client announces
  itself before its guild has replicated, so A1's nil-guild refusal produced a
  correct empty batch and A4's backoff latched "this server has nothing for my
  guild" and stopped asking. Both fixes are right; together they could have
  left a client permanently blank. The server declines to answer instead.

The pattern in all three is the same one the audit closes on: a value meaning
"not known yet" being read as a definite answer.

### CONFIRMED and NOT fixed: the picker's pager overlaps the item rows

The verification agent called this a mis-read of the original audit because the
row index is derived from `LIST_ROWS`/`LIST_PITCH`. The screenshot disagrees:
with "show all craftable items" on and eight pages, "< Previous / Next > /
page 1 of 8" is drawn ON TOP of the tenth and eleventh item rows.

The cause is the one the original audit named. The item tiles flow inside a
shell row host (`row_host(row, "ItemList", LIST_PITCH)`), while the pager is
placed on the CANVAS at `row * LINE`. Two coordinate systems with different
origins and different row heights - 40 against 34 - so no arithmetic on
`LIST_ROWS` reconciles them.

Not fixed, deliberately. The obvious home is the shell's `Foot` row, which the
rules pager already uses - but that row is 76 pixels for exactly two 34 pixel
rows, and making it taller is a change to the cooked widget in the pak, which
needs a UE editor this machine does not have. The alternative is flowing the
pager as an extra `ItemList` row, which is a layout refactor of the picker.
Either is a real piece of work and neither belongs at the end of a session that
has already introduced several regressions.

Impact: two item rows are obscured in one view. It does not affect the rules
screen, the grid, or any of the storage-only picker views.

### Reverted on the user's judgement

**C2, the pinned top edge, is reverted.** The audit was right that the tab strip
jumps 181 pixels between the rules list and the picker, and the fix worked - but
the result looked worse to the person using it: the panel sat high and the tall
picker hung a long way down the screen. The jump stays, knowingly. Where a
window sits is a matter of taste and the user outranks the audit on it.

If it is ever worth another attempt, the answer is a shell that reserves its
full height and lets the list scroll inside it, not arithmetic on the slot.

### Known: hot reload leaves an orphaned panel

`!pwp reload` swaps panel, overlay and icons. `reload.now` calls the OUTGOING
module's `overlay.hide()` and `overlay.reset()` first, but the old widget tree
stays on screen - a second, ghosted header and a stale row list sit above the
live panel, and closing and reopening does not clear it. A restart does.

Dev tooling only. A player never calls reload, and a world change reuses the
same module instance rather than swapping it, so nothing here reaches a
subscriber. Recorded because the reload path is how this mod is developed, and
a ghost panel during a test reads as a drawing bug in whatever was just changed.

### The chest sweep, measured (26 Aug, late)

Not in the original nine audits' ranked lists, and it is the only cost that was
measured on a live client rather than computed. The panel prints its own timing:

    panel refresh worst 48.0ms  (setup 0.0, hover 1.0/8, stock 47.0, draw 0.0)

Forty seven of forty eight milliseconds in one function. `walk_chests` ran
`accept(m)` before anything else, and for the per-camp caller that is a
`GetBaseCampIdBelongTo` plus a guid string build - paid for every wall, floor
and fence deriving from the container base class, which in a built-up base is
most of what the walk returns. The cheap test that excludes scenery came after.
The comment one line below already argued for the opposite ordering.

**Fixed, and measured again:**

    panel refresh worst 34.0ms  (setup 0.0, hover 1.0/34, stock 32.0, draw 1.0)

47ms -> 32ms, about a third. Less than hoped, because asking for the container
module is itself a reflected call on every object - the saving is the guid read
and the string, not the walk. The remaining cost is ~1500 objects at roughly
20 microseconds of reflection each, and only a smaller candidate set or a
longer-lived cache would move it further.

It is paid once when the panel opens, not per frame: the panel calls
`forget_stock()` on open deliberately, so the numbers a player is about to read
are current. That is the right trade at 32ms.

**Now the largest single cost is drawing the picker**, not the sweep:

    picker draw 35ms  (to search 1, search 0, rest of chrome 0, tiles 34, 18 tiles)

Thirty four milliseconds creating eighteen tiles, once, on switching to the ADD
tab. Not addressed.

## How to read a status

- **VERIFIED** — traced in the code by hand, independently of the agent that
  reported it. Quoted lines checked.
- **REPORTED** — one agent's reading, plausible, not independently confirmed.
- **CORROBORATED** — two or more agents reached it separately. The strongest
  signal in the set; every P0 below is one of these.
- **NEEDS MEASUREMENT** — cannot be settled by reading. The test is named.
- **REFUTED** — claimed and disproved. Recorded so it is not "found" again.

Line numbers are as of `b43578a` and will drift. The quoted code is the anchor.

## P0 — fix before anything else

### A1. The priority path fails open when the sender's guild cannot be resolved
`Scripts/main.lua:1509-1519`, `Scripts/main.lua:1354-1359`, `Scripts/net.lua:635`
**CORROBORATED** (multiplayer, security) · **VERIFIED**

The ownership check is `stand_rows(sender_guild)`, and `stand_rows` reads:

```lua
if want_guild == nil or camp_guild == want_guild then
```

`nil` means *every camp on the server*. `net.guild_of_sender` returns nil from
four separate points in `guild_via` (`net.lua:307-317`), and `guid_key` returns
nil for an all-zero GUID (`palapi.lua:104`) — which is what an unreplicated
guild id reads as. A player in no guild is an ordinary state, not an exploit.

So a guildless client is pushed every guild's roster, ranks and priorities, and
then passes the ownership check for any pal on the server. Ten edits per ten
seconds; a fifteen-pal rival base fully disabled in a couple of minutes.

This is the security defect already fixed once — "checked that a thing EXISTED
rather than that the sender OWNED it" — reintroduced through the nil path. The
comment at `main.lua:1500-1508` describes the fix that is being bypassed.

The asymmetry is the whole bug: the ceilings path refuses a nil guild outright
(`caps.lua:253-259`, `writable_guild`) and scopes reads closed (`caps.lua:485`).
`palapi.lua:444` states the rule that is being broken — *"Callers must read that
as 'no scope known', never as 'applies everywhere'."*

**Fix:** refuse rather than widen. Reject a non-string or empty `sender_guild`
in the `Prio` handler before `stand_rows`, make `net.push_pals` send nothing for
a nil guild, and give `stand_rows` an explicit `"*"` sentinel so `nil` can no
longer *express* "everything" from a network path.

### A2. Chat commands run with no sender check
`Scripts/main.lua:1925-1932`, dispatch at `main.lua:1243-1259`
**CORROBORATED** (multiplayer, security, silent failures) · **VERIFIED**

```lua
RegisterHook("/Script/Pal.PalUIChat:OnReceivedChat", function(context, message)
    local received = message:get()
    if not (received and received.Message) then return end
    handle_command(received.Message:ToString())
```

`handle_command` looks only at the text. No sender identity, no authority gate,
no rate limit. `OnReceivedChat` fires when the chat box *receives* a message,
and Palworld replicates chat to everyone.

On a **listen host**: another player types `!pwp adopt` and every wildcard
ceiling moves into the host's guild with the wildcard deleted — `caps.lua:421`
says plainly that adopting cannot be undone. `!pwp off` disables the mod
server-wide. `!pwp limit ...` writes the host's `caps.txt`.

On a **dedicated server**: a confused deputy. The attacker's chat line runs on
every other modded client, each of which submits a ceiling request under *its
own* guild. Every defence on the network path is satisfied, because the request
genuinely came from a member of that guild. The deliberate design at
`main.lua:1700-1703` — "The guild is deliberately not sent... which a client
cannot forge" — is walked around rather than broken.

**NEEDS MEASUREMENT:** confirm `OnReceivedChat` fires for *other* players'
messages. Two modded clients, one types `!pwp status`, check the other's log.
The fix is the same either way, because there is no sender check to fall back
on.

**Fix:** read the sender from the chat payload, act only on the local player's
own messages, and split `COMMANDS` into a safe read-only set and a privileged
set gated on "this came from this machine's own player".

### A3. Turning the mod off leaves every Pal fenced
`Scripts/main.lua:836`, `main.lua:872`, `config.lua:8`, `darnmenu.lua:69`
**REPORTED** (promises) · **VERIFIED**

`restore_all` is reachable from exactly two places: `!pwp off` and
`!pwp restore`. Nothing restores when `enabled = false` arrives from
`config.lua`, from `Mods/shared/PalWorkPriority_user.lua`, or via `!pwp reload`.

Both the config comment ("false leaves the game completely untouched") and the
DarnMenu label ("Off leaves every Pal exactly as the game left it") promise the
opposite. A player who unticks the box in DarnMenu and restarts gets a save
where every base Pal is still fenced with most work suitabilities unchecked,
recoverable only by hand on the stand.

`main.lua:826-832` documents this exact failure as fixed. The fix only ever
covered the chat command.

**Fix:** restore on the transition to disabled wherever it is read, not only in
`COMMANDS.off`.

### A4. `PWP_Hello` is unrated, and the client's retry never stops
`Scripts/main.lua:1442-1450` (server), `Scripts/ui.lua:794-821` (client)
**CORROBORATED** (multiplayer, security) · **VERIFIED**

`may_change` gates `Prio`, `Set` and `Clear`. It does not gate `Hello`, which is
the most expensive message the server handles: two full `FindAllOf` transmitter
walks, a base-camp walk, and fourteen native rank calls per pal. Conservatively
40-60 ms of game thread each, on a populated server. A client can send them in a
loop and freeze the server for everyone.

The client half is self-inflicted and was **added in `b43578a`**. The re-ask
fires whenever `net.pals` is empty, which for a guild with no loaded camps is
*permanently*, so it repeats every ten seconds for the whole session — and it
sits above the `menu_likely_open` early return, so it runs whether or not a
stand was ever opened. The comment claims the opposite: *"a server that
genuinely has no pals for this guild is not asked repeatedly."* That is the one
case where it is asked forever.

**Fix:** budget `Hello` separately and tightly (it is a once-per-spawn message);
back the client's re-ask off exponentially and stop once the server has answered
once with an empty batch.

### A5. `world_key` may not distinguish two sessions, which would make the authority memo a crash
`Scripts/palapi.lua:407-418`, `Scripts/main.lua:1735-1767`
**REPORTED** (multiplayer) · **NEEDS MEASUREMENT**

`world_key` is `world:GetFullName()`, derived from the map package path.
Palworld runs one persistent map. If that string is the same for single player
and for a dedicated server, then `switched` is false for every transition after
the first spawn, and the entire reset block never runs again — `api.reset`,
`net.reset`, `panel.reset`, `overlay.reset` become dead code on reconnect.

The consequence that matters: `api.reset()` is the only thing that clears the
`auth` memo added in `b43578a`. Host a session, quit, join a dedicated server,
and `auth` stays `true`. The pass timer is still armed, so a pass can run on a
client with authority answering a stale `true` — reaching `GetNickname` and
`suitability_rank` on replicated pal proxies. That is the uncatchable access
violation this codebase is arranged around.

Secondary: `net.reset()` never runs either, so `net.pals` carries over from the
previous server and the client never re-announces.

**The measurement, five minutes:** log `api.world_key()` on entering single
player, then on joining the dedicated server, and compare the strings. If they
differ, this finding collapses to nothing. If they match, it is the most severe
item in this file.

**Fix if confirmed:** fold something connection-specific into `world_key`, and
stop the memo being load-bearing for safety — give `scheduler.run_pass` its own
unmemoised authority probe, as `scheduler.restore` already has.

### A6. A pal's permission is switched off for the work it is doing right now
`Scripts/scheduler.lua:553` (the toggle loop), `scheduler.lua:361-390` (`keeps`),
`scheduler.lua:441` (the fence is one level)
**VERIFIED** · reported by a player, 26 Aug · **FIXED** in the toggle loop

Added after the first pass of this audit, from a Workshop comment:

> "All of my electric pals will occasionally just stop working in generating,
> and I can't force them either... it will display the original interface,
> showing the job as disabled, but then switch to the new numbered priority
> where I have set to 1, but the pals still act as if it's disabled."

The chain is ours end to end. A generator is a **continuous** station: one work
object, and once it is manned it stops asking for a worker, so no further demand
pulse arrives. A furnace or a mine makes a fresh work object per item and keeps
pulsing, which is why neither ever shows this. `demand.lua` already records the
variance - "all 77 gathering works pulsed while only 2 of 16 lumbering works
ever did"; the generator is the far end of that scale.

With demand at zero, `keeps()` stops restarting the hold clock and the type ages
out at `HOLD_SECONDS = 90`. Note the expiry is only ever **reachable** for a pal
that is currently doing the work, because `keeps` returns false above it when
`pal.current ~= value`. So the one case the hold exists to protect is the only
case it can fail. The type then drops out of the fence, the fence is a single
priority level, and the toggle loop switches off the permission of a pal that is
at that moment generating power.

The second half of the report is `ui.lua:507`. The grid hides the vanilla
checkbox and rebinds the click to cycling priority, so the player sees a "1"
painted over a checkbox the mod has just unticked and has no way to correct it.
"For a brief moment it will display the original interface" is that hide racing
the paint - they are seeing the truth for one frame.

**PalPriority (Nexus 3830) cannot produce this**, and the difference is not the
engine call - both mods enforce with `RequestChangeWorkSuitability_ToServer` and
neither uses fixed assignment. The difference is the planner. `planner.lua:147`
keeps every type at or above the claimed bar enabled regardless of demand, so a
priority-1 type can never be switched off; and `planner.lua:151-153` has an
explicit `protectCurrent` that ORs the currently-performed type into the enabled
mask. Two independent guards. Ours had neither, and its hold expiry actively
removed the protection. Their planner fails open, ours failed closed.

**Fixed** by protecting `pal.current` in the toggle loop, which restores the
contract the comment above `keeps()` already states: *"to KEEP a pal where it is
takes only that work of that type still exists."* X still wins - a type the
player marked never is switched off even mid-job.

**Not yet done, and worth deciding separately:**
- Widen the fence to "this level and everything more important"
  (`scheduler.lua:441`), matching `planner.lua:147`. A priority-1 type should
  not be off while the pal does priority-3 work. This changes scheduling
  semantics, so it is a decision rather than a fix.
- `ui.lua:507` should not conceal a permission the mod has switched off.
  Concealing it is what turned a recoverable stall into "I can't force them".
- The Workshop description promises *"a pal already working keeps its job rather
  than being pulled off mid-task"*, which is the exact sentence this violated.

**Correction to this file:** the Glave entry under "What players actually
reported" was recorded as a misunderstanding, and that verdict stands for Glave -
a ranking surprise. It was wrong to generalise it. This report is a permission
being withdrawn from a pal actively doing the job, which is a defect.

## P1 — data loss, denial of service, and a shipped stutter

### B1. File loaders admit values with no integer representation, and the writer uses `%d`
`Scripts/store.lua:45-52` + `store.lua:105`; `Scripts/caps.lua:110-111` + `caps.lua:185`
**REPORTED** (security) · **REPORTED**

The known corruption defect was fixed at the network door (`main.lua:1489-1494`)
and not at the sink. One hand-edited line —
`abc123|99999999999999999999|3` — loads cleanly, because `tonumber` yields a
float and nothing checks for an integer representation. The next save then:

1. `io.open(path, "wb")` truncates the file,
2. `string.format("%s|%d|%s", ...)` throws,
3. `dirty_at = nil` is never reached, the handle leaks,
4. `store.flush()` retries every tick — truncate, throw, leak, forever.

Every priority on the machine is gone from disk for the session and no future
edit can be saved. `caps.txt` is worse: `caps.save` is not debounced, so the
first accepted rule change destroys every guild's ceilings, and the throw is
swallowed by a bare `pcall` so nothing is logged.

These files are documented as hand-editable and the sort order exists so a hand
edit survives. A fat-fingered digit is enough; no malice required.

**Fix:** `math.tointeger` with explicit ranges in both parsers, and make the
writers skip and warn about a row that will not convert rather than losing the
file.

### B2. Every data write is non-atomic
`Scripts/store.lua:83-113`, `Scripts/caps.lua:156-191`, `Scripts/darnmenu.lua:149-161`
**REPORTED** (security)

Truncate-then-write with no temp file and no rename. This process has died
mid-operation before — `docs/the-crash.md` exists because of it — and
`discover.lua:605` calls `unbuffered(f)` specifically so a dump survives a crash
mid-write, so the risk is understood elsewhere in the codebase.

The DarnMenu index is the worst case: a crash mid-write leaves
`DarnMenu_schema_index.lua` empty and **every mod's settings page disappears**.

**Fix:** write to `.tmp`, close, rename. Three lines each. It also contains B1's
blast radius.

### B3. `loadfile` executes a user-editable file with bytecode and full globals
`Scripts/darnmenu.lua:140-145`, `Scripts/main.lua:152`
**REPORTED** (security)

`loadfile(path)` defaults to mode `"bt"`, so it will load precompiled bytecode —
Lua 5.4's verifier is not a security boundary — and the chunk runs with
`_ENV = _G`, reaching `io`, `os.execute` and the whole UE4SS surface.
`darnmenu.lua:214` calls the file "player-editable" and says it "refuses rather
than trusts", but the refusal happens *after* the file has run.

Local-only, so the realistic threat is a trojanised settings preset shared
between players or a hostile mod writing into the shared directory.

**Fix:** `loadfile(path, "t", {})`. One line, complete for a file that should
only ever return a literal table.

### B4. `icons.lua` saturates the game thread while the picker is open
`Scripts/icons.lua:316`, and the feeder at `icons.lua:500-555`
**REPORTED** (performance) · matches a real player report

`pump_one` does one `StaticFindObject` per name purely to record whether a
`LoadAsset` landed. At `PUMP_BATCH = 12` and `PUMP_MS = 100` that is 120
lookups a second at 9-12 ms each — **1.0 to 1.4 seconds of game thread per
second**. The clock cannot keep up.

It was never caught because `M.finds` / `M.find_ms` are initialised and **never
incremented**, so the bench prints "0 finds, 0.00ms average" while this runs.

Worse, a throttled sweep clears `frame_tex` and sends every already-loaded icon
back through `want()`, re-queuing up to 187 a second against a drain rate of
120 — so the queue grows faster than it empties and the saturation does not end
while browsing.

`icons.lua:519` states why the lookup is unnecessary: *"FindAllOf and
StaticFindObject read the same object array, so if the sweep did not see it, it
is not loaded."*

**Fix:** delete the `StaticFindObject`; fill `arrived` from the sweep that is
already paid for. Return early on a throttled sweep instead of falling into the
miss path.

### B5. `remote.txt` is opened every second, all session, on every subscriber
`Scripts/main.lua:52`, `Scripts/remote.lua:155`
**REPORTED** (performance, Workshop comments) · matches a real player report

`remote.path` is wired unconditionally — there is no dev flag — so a
developer-only control channel does a synchronous open/read/close once a second
in every shipped copy. Small per call, but it is pure waste in a release build,
it is one more thing that can block on a stalled filesystem, and it is the best
structural match for the "micro-stutters every second in the open field" report
on the Workshop page.

**Fix:** gate on a config flag, or stat once at load and skip when absent.

### B6. On a client, every mouse click in the game costs a full array walk
`Scripts/ui.lua:886`, `ui.lua:852-863`
**CORROBORATED** (performance, bugs)

`M.refresh` returns at the generation check *before* it reaches `live_menu()` —
the only thing that clears `menu_likely_open`. So on a client, once the stand
has been opened and painted once, the flag stays true and **every left click for
the rest of the session** pays a `FindAllOf` over the cell class plus ~400
reflection calls: 15-25 ms, stand open or shut.

The same early return means `forget_injected` is never called, so `cell_text`
can hold widgets of a destroyed menu instance that only the click path touches —
an `IsValid()` on a stale wrapper, which is the crash.

**Fix:** clear the flag on the client path too, and move `painted_gen` assignment
to after a successful repaint so a consumed generation with no draw cannot latch.

## P2 — user-visible UI defects

### C1. The panel opens as an empty full-height slab, then collapses 360 px
`Scripts/panel.lua:4310-4333`, `Scripts/overlay.lua:1039`, `overlay.lua:1162`
**REPORTED** (UI) · **VERIFIED from screenshots**

`M.toggle` makes the shell visible and returns without drawing; the first
content lands on the next 100 ms beat. Measured from
`ScreenShot00305.png`: the empty slab is 1146×700, the settled RULES screen is
1146×340. `overlay.height` is never reset on close, so after one visit to the
ADD tab every subsequent open starts at 700.

**Fix:** draw synchronously inside `toggle` before `overlay.show()`, and reset
`overlay.height` on close.

### C2. The tab strip jumps 181 px between RULES and ADD
`Scripts/overlay.lua:1055-1069`
**REPORTED** (UI) · **VERIFIED from screenshots**

The Backdrop slot is centre-anchored and `fit_width` sets only its size, so half
of every height change moves the top edge — the tab you just clicked moves out
from under the pointer. `panel.lua:4187-4193` records this exact regression as
already fixed, but that fix lives on the hand-built canvas path, which never
runs once the pak is installed.

**Fix:** anchor the top edge so growth goes downward only. Shares a cause with
C1.

### C3. The only destructive control loses its danger colour when armed
`Scripts/panel.lua:1289-1294`
**REPORTED** (UI)

```lua
local shown = (selected and not key:match("^tab_")) and "hover" or colour_key
```

Whatever colour the caller asked for is discarded for the hovered element. So
`Remove`, drawn red once armed, turns cyan the moment the pointer is on it —
one click from firing.

**Fix:** carry selection on the stripe, rail and caret, which already exist.
Never overwrite a token's own colour.

### C4. Armed `Remove` never visually disarms
`Scripts/panel.lua:5703-5712`
**REPORTED** (UI)

The four-second window is evaluated only on the *next* click, so a row shows
`Sure?` indefinitely and a later click re-arms rather than deleting. Nothing
changes on screen, so it reads as a dead button.

**Fix:** clear `pending_drop` in `refresh` once the window has passed. One line.

### C5. "Show every item with a job" has no visible state, and a refused click says nothing
`Scripts/panel.lua:3708`, `panel.lua:5558`
**REPORTED** (UI) · **VERIFIED by pixel diff**

The state is one character, `[x]` versus `[ ]`, in the same colour as its own
label, in a glyph slot the row below uses for a `<` caret. A programmatic diff
of two screenshots taken across a toggle attempt shows **zero** differing pixels
in the checkbox row.

The click was addressed as `every`; the real target is `toggle_all`, a name that
appears nowhere on screen and is missing from `COMMANDS.click`'s usage string.
`click_named`'s refusal goes to `log.say` — a file no player has open.

**Fix:** draw a real filled box. Route `click_named`'s failure through
`announce()` so a refused action says so on screen.

### C6. The two halves of the mod do not talk to each other
`Scripts/ui.lua:494-495`
**REPORTED** (UI)

`cap_set` and `cap_none` were written so a capped job is marked on the grid, with
a comment explaining the colour choice. They are referenced **nowhere**. So the
panel says Lumbering is `Stopped` while the grid shows a priority 4 for it.

### C7. Smaller UI items, in rough order

- No legend for which mouse button does what (`ui.lua:948-980`); documented only
  in the README and on the Workshop page.
- Full gamepad support with zero on-screen prompts (`pad.lua:199-227`), in a game
  that draws a keycap row on every menu.
- Item names differ between screens: the picker uses `pretty_name`, every
  `announce()` uses the raw id, so picking "Mushroom Quiche" confirms
  `Mushroom_Quiche`.
- The picker's pager is the only control still at an absolute canvas position
  (`panel.lua:3608-3649`); it does not track the grid height and only bites once
  "show every item" is on.
- Notices never render on the picker screen — `RB.use_row("Notice")` exists only
  inside `draw_list` (`panel.lua:2801`), so the announce fired on entering the
  picker goes to a buffer that screen never draws.
- The shipped backdrop is 8% transparent. `panel.lua:483` sets `A = 0.985` with a
  comment insisting on near-opacity, then bails at `panel.lua:796` in every real
  session; the surface actually drawn is baked at `A = 0.92` in the commandlet.
- "Show every item with a job" reads as a Pal's work type. "Show all craftable
  items" is what it means.

## P3 — correctness and hygiene

- **`panel.handle_click` has no freshness gate** while its sibling `hover_tick`
  does (`panel.lua:5491` vs `3888-3893`). A click landing in the window between
  a world transition and the next refresh reaches `IsValid()` on a freed widget.
  One line, copied from the sibling. *(bugs, HIGH — promoted here only because
  it needs the timing to fire.)*
- **`scheduler.run_pass` has no authority gate** while the less dangerous
  `M.restore` does (`scheduler.lua:1009` vs `633-639`). Latent — the only caller
  gates — but `restore`'s own comment argues a public primitive must not depend
  on caller discipline.
- **A fractional `work_caps` value silently kills all rule sync**
  (`main.lua:102-107`). `validate` warns about the type and does not drop the
  value; it reaches `%d` in `push_rules`, throws inside a `pcall`, and no client
  receives any ceiling for the session with nothing in the log.
- **A fractional `work_priority` is inert and corrupts the click that touches
  it** (`main.lua:87`, `store.lua:238-241`). `2.5` never equals any level, so the
  pal is never fenced; one click writes `1.5`, which the loader's `(%w+)` will
  not match, so the line is silently dropped next launch.
- **`net.to_server` keeps the component fallback that the pass removed as
  proven-broken** (`net.lua:197-202`). `scheduler.run_pass` and `restore` both
  deleted it because Unreal drops those RPCs silently while `sent_up` still
  counts them. This is the one send site whose result is reported to the player
  as success.
- **A single failed push evicts a client permanently** (`net.lua:852-873`).
  Nothing re-adds them except an inbound message, so a player who joins and then
  simply plays sees a frozen panel for the session.
- **No full stand re-push exists** (`main.lua:1447` is the only one). A pal
  caught after the client's Hello never appears; a pal removed shows numbers
  forever.
- **The protocol width is hardcoded to 14** in three places against
  `#workdefs.ORDER` (`net.lua:606`, `net.lua:725`).
- **`panel.lua` is at 198 top-level locals**, not the "four short" its own
  comment claims. Two slots left before hot reload breaks silently.
- **`api.game_ui_active` is a cross-module field palapi never declares and never
  resets** (`main.lua:1901-1922`). Written only inside a discarded pcall inside a
  hook whose registration failure is debug-only; if both hook paths fail it stays
  nil forever and the cursor is restored over the game's own menus.
- **`ExecuteWithDelay` bypasses `clock.lua`** (`panel.lua:4805`), against the
  rule stated at `clock.lua:26`. Diagnostic path only.

## Refuted — do not "find" these again

### R1. The server does NOT double-push on every edit
Claimed by the performance audit: `store.apply_set` fires `on_change` →
`push_stand`, and then `main.lua:1554` pushes again, so every client edit costs
two pushes.

**Disproved by the server log.** Each `priority ... by a player` is followed by
exactly one `stand push: 1 row of 14`, never two. `push_stand` logs once per
call, so only one call happens: `store.on_change` is **not firing on the
authority**. This matches instrumentation from earlier the same day, and it is
why the explicit push at `main.lua:1554` must stay — removing it once already
resulted in nothing being pushed at all.

The comment at `main.lua:1545-1553` is correct as written.

### R2. `api.reset()` is called
The multiplayer audit stated nothing calls it. `main.lua:1746` does, in the
world reset step list. This matters because it is what makes the `auth` memo
safe to clear — see A5.

## Ship blockers for 0.4.0

Order matters; step 1 protects the rollback that step 4 destroys.

1. **Back up the staging folder first.** The only complete published 0.3.0
   package on this machine is
   `steamapps/workshop/content/1623730/3786408856`, and the upload procedure
   copies 0.4.0 over it. The pak has never been committed to git — it exists in
   three places, all on this machine, all identical bytes.
2. **Bump the version in both places.** `Info.json:5` and `Scripts/main.lua:34`
   both still read `0.3.0`, and the banner is a hardcoded Lua literal, not read
   from `Info.json`. The loader compares `Version` as a plain string, so
   publishing unchanged delivers nothing to any subscriber.
3. **Fix the four strings that state the opposite of how the mod behaves.**
   `README.md:675-677` ("the grid is switched off entirely on a client"),
   `main.lua:1846-1850`, `ui.lua:752`, `ui.lua:782`. All false since `fb9033c`.
   The README ships in the package, so it is public.
4. **Sync staging** — seven files differ, precisely the multiplayer work, and
   the staging `Info.json` has **no** `IsServer` rule at all.
5. **Write a changelog.** None exists. Five commits are unpublished, and server
   owners need telling to update the server too: there is no protocol version
   negotiation in `net.lua`.
6. **Add a dedicated-server install section to the README.** It has none, and
   nothing tells an admin the mod must be installed server-side — the most
   likely cause of "doesn't work on my server".
7. `python tools/luacheck.py 'Scripts/*.lua'` → exit 0.
8. `python tools/pakcheck.py` → exit 0, "ok, identical to the pak the game is
   running". The pak is currently correct and unchanged since 0.3.0.
9. Byte-compare staging against the repo, then upload, then tag. Neither 0.2.0
   nor 0.3.0 was tagged.

**UNVERIFIABLE LOCALLY:** whether `IsServer: true` actually installs on a
subscriber's dedicated server. The declaration is well-formed and matches four
other published mods verbatim (BaseRadiusImproved, InfiniteWeightInCamp,
SmartPalFeeding, TrueMercy). Only an install proves it.

**Decide rather than discover:** AutoHatch — the mod the README names as the one
to copy — also declares a *server* `LogicMods` rule. This mod does not. That is
probably right, since the pak carries only the UI widget and a headless server
draws none, and CreativeMenu omits it too. But make it a decision.

## The lesson worth keeping

Two independent audits reached A1 and A2 separately, and both are the same
underlying mistake the postmortems in this repo already name: **deriving scope
from something other than the authenticated sender, and treating "I could not
determine the scope" as "all scopes" rather than "refuse."**

The ceilings path learned it. The priority path and the chat path did not.
